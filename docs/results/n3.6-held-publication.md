# C2-T: hold virtqueue publication in deadline/cancellation tests

Status: test-design correction accepted for final N3 verification.
Production and protected Gate B/C/D binary identities are unchanged.

## Original failure

The first final D1 campaign stopped in `vblk-writable` at
`scope: IRQ wait uses the earlier whole-operation deadline`.
The request completed instead of reaching the intended deadline.
The original failed root `n36-final-d1-20261022T222934Z` remains sealed and
archived as a failed/incomplete attempt. Its result has not been rewritten.

The test suppressed a notification and assumed the request could not complete.
That assumption is invalid: a request whose available-ring index is already
published is visible to the device. Suppressing a doorbell is not a publication
barrier. The retained QEMU 10.2.1 investigation found a queue kick when DRIVER_OK
attaches its host notifier; that kick can consume already available requests.

## Corrected test mechanism

Only the four relevant test images compile the hook: `vblk`,
`scope-orphan-idle`, `file` and `ext2`. The unchanged production path does not
compile it. Neither do the accepted Gate B/C/D images.

1. `vblk_test_hold_publish()` requires a READY, unheld queue and copies the
   available ring into fixed private test storage.
2. Submissions update that private ring. The real device-visible index stays
   unchanged, so an unrelated kick cannot discover the held submissions.
3. A late-completion test calls `vblk_test_publish_held()` before notifying.
   It copies entries in ring order, including 16-bit wrap, then uses barriers to
   publish ring entries before the index, following virtio 1.2 §2.7.13/§2.7.13.3.
4. Reset/reinitialization invalidates the hold; stale requests are never
   republished into a new queue.

The original exception that intentionally permits a real request to complete
remains explicit. Assertions, expected errors, deadlines, cancellation debt and
exact retirement checks were retained. No production driver workaround or
feature was introduced.

## Existing verification evidence

`scripts/test-vblk-held-publication.py` exercises the real hook in a host
harness: hold/release, ordering and wrap, flags, reset/not-ready invalidation,
unheld release and misuse panics. It checks all held/late-delivery sites and
preprocessor confinement. The accepted repair records report 7/7 new host tests,
14/14 detected mutations, unchanged protected preprocessing and seven reference
identities, 139 frozen hashes and valid layouts.

The targeted unchanged `vblk-writable` recipe passed:

- Guest exit 33 and all five required markers.
- 166/166 virtio-blk cases and 73/73 block cases.
- Nine expected timeouts, intended protocol-error controls and scope-deadline resets.
- No guest panic and no change to the attached writable-device image.

The successful targeted run was sealed in
`n36-final-qval1-20261023T082435Z`; the separate repair checkpoint is
`n36-final-repair2-20261023T074953Z`. Full manifest/archive hashes and scope
are in [n3-evidence.json](n3-evidence.json). Targeted archive verification is
78/78 tier-1 members; repair archive verification is 331/331.

The repaired full D1a–D1f results were subsequently accepted. The unfinished
D1r3 root was never sealed or archived; completed results and screenshots were
copied into the accepted finalization root with provenance. See
[final closure and failure history](n3-closure.md).

Reproduction uses the preserved source, exact tool/build environment, original
recipe and admitted controller. No test was rerun to write this explanation.
